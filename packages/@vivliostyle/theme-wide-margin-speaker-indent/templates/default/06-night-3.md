# ビルドが壊れた夜 {#night-3}

<p class="chapter-lead">二〇二六年十月二十九日／CIのビルド</p>

## 二十二時の赤

<div class="dialogue">

<span class="speaker">柊</span>まず状況から共有するね。二十二時ちょうど、mainのCIが赤くなった。エラーは依存解決のところで止まっていて、あるパッケージのバージョンが見つからない、と言って落ちてる。

<span class="speaker">真砂</span>ローカルでは再現しないやつ？

<span class="speaker">柊</span>そう。手元だと何事もなくビルドできる。同じコミット、同じコマンドなのに、CIのログだけが存在しないバージョンを探しにいって失敗する。

<span class="speaker">真砂</span>その時点では、みんなレジストリ側の障害を疑ったんだよね。落ちる場所がいかにもそれっぽいから。

<span class="speaker">柊</span>いかにもそれっぽかった。しかもその日は、翌朝にリリースを控えてた。mainが赤いままだと出せない。

<span class="speaker">真砂</span>直前に入った変更は。

<span class="speaker">柊</span>二十一時五十二分に、共通UIライブラリを2.4.0から2.5.0に上げる変更がマージされてる。ロックファイルも一緒に更新されてた。

<span class="speaker">真砂</span>それが原因だと思うよね、普通は。

<span class="speaker">柊</span>思う。だから最初にやったのは、その変更を戻したらどうなるか。戻せばmainは緑に戻るはずだった。

<span class="speaker">真砂</span>戻らなかった。

<span class="speaker">柊</span>戻った。緑になった。それで安心して、その日は終わりかけた。

<span class="speaker">真砂</span>安心しちゃだめなやつだ。

<span class="speaker">柊</span>だめだった。だって、その変更自体はどこも悪くない。PRのビルドは通ってるんだから。戻すのは対処であって、答えじゃない。

</div>

<div class="note">

この夜の対応が長引いたのは、原因が「いつもの場所」になかったからだ。ログはたしかに依存解決の失敗を告げていたが、当の依存そのものは何も壊れていなかった。記録によれば、最初の一時間はほぼ全員がレジストリの状態ページを見つめて過ごしている。

</div>

## レジストリを疑う

<div class="dialogue">

<span class="speaker">柊</span>結論から言うと、レジストリは生きてた。試しに問題のパッケージを直接叩いてみたら、ちゃんと目的のバージョンが返ってくる。

<span class="speaker">真砂</span>じゃあネットワークでもレジストリでもない。

<span class="speaker">柊</span>うん。プロキシもDNSも問題なし。切り分けを進めるほど、犯人が一人ずつ消えていく感じだった。

<span class="speaker">真砂</span>そのとき、ランナーの中には入ってみた？

<span class="speaker">柊</span>入った。ランナーを一台つかまえて、手で同じコマンドを打った。そうしたら通る。

<span class="speaker">真砂</span>通るんだ。

<span class="speaker">柊</span>通る。同じ機械の、同じネットワークで、手で打つと通って、パイプラインから走ると落ちる。ここが一番わけが分からなかった。

<span class="speaker">真砂</span>それ、たいてい環境変数か設定ファイルの違いだよね。

<span class="speaker">柊</span>そう思って、環境変数を全部並べて突き合わせた。二十分かけて、差はなかった。

</div>

<div class="note">

このとき二人が比べていたのは、ランナーの中の環境と自分の手元の環境だった。パイプラインが実行前に何をしているか、という一段外側は、比較の対象に入っていない。あとから見れば、答えはその外側にあった。

</div>

## 白ばかりが増える

<div class="dialogue">

<span class="speaker">真砂</span>零時をまわったあたりだよね、たしか。

<span class="speaker">柊</span>まわってた。そのころには、疑ったものの一覧がホワイトボードに十個くらい並んでて、全部に横線が引いてあった。レジストリ、ネットワーク、プロキシ、DNS、ランナーの世代、依存のバージョン、ロックファイルの壊れ、時計のずれ。

<span class="speaker">真砂</span>時計まで疑ったのか。

<span class="speaker">柊</span>疑うものがなくなると、時計を疑うんだよ。

<span class="speaker">真砂</span>そこで一回、手を止めたんだよね。そもそも問いの立て方が合っているのか、って。

<span class="speaker">柊</span>止めた。ホワイトボードの横線を見てて、これは候補が尽きたんじゃなくて、候補の出し方が間違ってるんだと思った。

<span class="speaker">真砂</span>どう変えたの。

<span class="speaker">柊</span>何が壊れているかを探すのをやめて、手元とCIで違うものを全部書き出すことにした。壊れているかどうかは関係なく、違うものを全部。

</div>

<div class="note">

障害対応の現場では、切り分けが進むほど手詰まりに見えることがある。疑わしい箇所をひとつずつ潰してどれも白だったとき、残るのは「前提のどこかが間違っている」という可能性だけになる。

</div>

## 読み飛ばしていた一行

<div class="dialogue">

<span class="speaker">柊</span>ログを頭から読み直した。すると失敗する直前に、ふだんは読み飛ばす一行があった。「キャッシュを復元しています」。

<span class="speaker">真砂</span>CIのビルドキャッシュか。

<span class="speaker">柊</span>そう。しかも復元したキャッシュに、保存された日付が出てた。十月八日。

<span class="speaker">真砂</span>三週間前。

<span class="speaker">柊</span>三週間前のものを、その夜のビルドが正だと思って使っていた。

</div>

```text title="ビルドのログ（抜粋・訳出）"
[00:00:03] キャッシュを復元しています: deps-x86_64 (2026-10-08 保存)
[00:00:19] 依存を解決しています (ネットワーク: 無効)
[00:00:21] エラー: 共通UIライブラリ 2.5.0 が見つかりません
[00:00:21] ジョブは失敗しました (経過 21 秒)
```

<div class="dialogue">

<span class="speaker">真砂</span>二行目、ネットワークが無効になってる。

<span class="speaker">柊</span>そこが二つめの発見だった。三週間前に、CIを速くするための変更が共通のパイプライン定義に入ってる。依存の解決をキャッシュだけで済ませて、レジストリには問い合わせない設定。

<span class="speaker">真砂</span>速くはなったの。

<span class="speaker">柊</span>なった。一回あたり四十秒くらい縮んだ。悪い変更じゃないんだよ、単体では。

<span class="speaker">真砂</span>じゃあ、キャッシュの中には2.5.0が入っていないのに、外に取りにいくこともできない状態だった。

<span class="speaker">柊</span>そういうこと。パッケージマネージャから見ると、自分が知っている一覧に2.5.0が載っていない。だから返す答えは、そんなバージョンは存在しません、になる。

<span class="speaker">真砂</span>レジストリが落ちているときと、まったく同じ文面が出るわけだ。

<span class="speaker">柊</span>同じ文面が出る。あの三時間の半分は、この文面のせいだと思ってる。

</div>

<div class="note">

依存が見つからないという表示は、レジストリに存在しない場合と、こちらから問い合わせていない場合の両方で出る。前者は相手の問題であり、後者はこちらの設定の問題だが、利用者に見えるのは同じ一行である。エラーメッセージが原因の場所を指し示すとはかぎらない。

</div>

## キャッシュの中の三週間前

<div class="dialogue">

<span class="speaker">真砂</span>そこまで分かって、確かめたのは。

<span class="speaker">柊</span>キャッシュを使わない設定で同じビルドを流した。二分待って、緑。

<span class="speaker">真砂</span>それで確定だ。

<span class="speaker">柊</span>確定。零時五十五分。ここまでで三時間近く経ってた。

<span class="speaker">真砂</span>キャッシュのキーはどうなってたの。

<span class="speaker">柊</span>`deps-`のあとにランナーの種類を付けただけ。`deps-x86_64`。それだけ。

<span class="speaker">真砂</span>依存の内容がキーに入っていない。

<span class="speaker">柊</span>入っていない。だから、依存が何に変わろうと同じキーを引く。しかもうちのCIは、同じキーのキャッシュがすでにあるときは上書きしない仕様だった。

<span class="speaker">真砂</span>じゃあ十月八日のものが、その後ずっと残り続けたのか。

<span class="speaker">柊</span>残り続けた。三週間、誰も依存を触らなかったから、誰も困らなかった。

</div>

## なぜ昨日まで平気だったのか

<div class="dialogue">

<span class="speaker">真砂</span>そこ、いちばん聞きたかったところ。壊れる仕込みは三週間前からあったのに、なんで昨日の夜まで何も起きなかったの。

<span class="speaker">柊</span>条件が三つ揃う必要があったから。一つめ、キャッシュのキーに依存の内容が入っていないこと。これは最初からずっとそう。

<span class="speaker">真砂</span>二つめが、ネットワークを使わない設定。

<span class="speaker">柊</span>三週間前に入った。ここまでは、まだ何も起きない。キャッシュの中身とロックファイルが一致しているうちは、外に問い合わせる必要がないんだから。

<span class="speaker">真砂</span>三つめが、依存の更新。

<span class="speaker">柊</span>それが二十一時五十二分。この瞬間に、ロックファイルはキャッシュより新しくなった。三つ揃った。

<span class="speaker">真砂</span>PRのビルドが通ってたのは。

<span class="speaker">柊</span>キャッシュのキーにブランチ名が入っていたから。新しいブランチにはキャッシュがなくて、ゼロから解決される。ゼロから解決するときはネットワークを使うから、2.5.0はちゃんと取れる。

<span class="speaker">真砂</span>PRでは正しく動いて、mainに入った瞬間に壊れる。いちばん見つけにくい形だ。

<span class="speaker">柊</span>しかも、そのときのキャッシュはブランチ用のキーで保存されて、mainのキーには何も残らない。mainのキャッシュは十月八日のまま。

</div>

<div class="note">

事故の直接の引き金は依存の更新だが、それを事故に変えたのは三週間前の高速化と、最初からあったキャッシュキーの設計である。単独では無害な三つの判断が、時間をおいて一つの失敗になった。三週間という間隔が、変更と結果を結びつけることをいっそう難しくした。

</div>

## 三行の修正

> 落ちるのはコードじゃなく、前提のほうだった

<div class="dialogue">

<span class="speaker">真砂</span>つまりコードは一行も間違っていなかった。間違っていたのは、キャッシュは常に最新である、という誰も口に出さない前提のほう。

<span class="speaker">柊</span>そういうこと。キャッシュのキーにロックファイルのハッシュを含めるようにして、それで再発は止まった。直し自体はわずか三行だった。

</div>

```yaml title="ci/pipeline.yml — 再発を止めた三行"
cache:
  key: deps-\{{ runner.arch }}-\{{ checksum "deps.lock" }}
  paths: ['.pkg-store', '.pkg-meta']
```

<div class="dialogue">

<span class="speaker">真砂</span>ロックファイルが変われば、キーも変わる。

<span class="speaker">柊</span>変わる。キーが変われば、そのキャッシュは存在しないから、ゼロから解決される。依存が変わっていない日は今までどおりキャッシュが効く。

<span class="speaker">真砂</span>速さは落ちない。

<span class="speaker">柊</span>落ちない。依存を更新した日だけ四十秒遅くなる。それは払っていい。

<span class="speaker">真砂</span>原因にたどり着くまでが三時間で、直すのが三行。障害対応って、だいたいそういう時間の配分になるよね。

<span class="speaker">柊</span>なる。それと、三行の中身より三行を書ける状態になるまでが本体だと思ってる。

</div>

## 次の夜のために

<div class="dialogue">

<span class="speaker">真砂</span>再発防止としては、キーの修正のほかに何を入れた。

<span class="speaker">柊</span>四つ。一つめは、ネットワークを使わない設定をやめて、キャッシュにないものは取りにいくように戻した。速さのために正しさを削るのは、削っていい場面を選ばないと危ない。

<span class="speaker">真砂</span>二つめは。

<span class="speaker">柊</span>キャッシュを使わずに再実行するボタンを、誰でも押せる場所に置いた。押せば十分で切り分けが一つ終わる。あの夜、これがあれば三時間が三十分だった。

<span class="speaker">真砂</span>三つめ。

<span class="speaker">柊</span>ログの読み方。復元しています、という行の直後に、そのキャッシュがいつ保存されたものかを必ず出すようにした。もともと出ていたんだけど、行末に小さく出ていて誰も見ていなかったから、独立した行にした。

<span class="speaker">真砂</span>四つめは、たしか一覧を作ったんだよね。

<span class="speaker">柊</span>手元とCIで違うものの一覧。設定ファイル、環境変数、ネットワークの可否、キャッシュの有無、時計。作るのに半日かかったけど、次に「手元では動く」が起きたとき、最初に開くのはこれになる。

</div>

<div class="note">

この一覧は、その後の半年で三度参照されている。うち二度は、一覧に載っていた項目がそのまま原因だった。残る一度は載っていなかった項目が原因で、その日のうちに一行が書き足された。

</div>

<div class="dialogue">

<span class="speaker">真砂</span>そういえば、翌朝のリリースはどうなったの。

<span class="speaker">柊</span>出した。一時二十分に緑になって、そのあと三十分だけ議論した。原因が分かった直後にそのまま出していいのか、と。

<span class="speaker">真砂</span>直したのはCIの設定で、製品のコードじゃないもんね。

<span class="speaker">柊</span>そう。だから出せる、という理屈と、怖い、という感覚が半々だった。最後は、ビルドが緑である理由を全員が説明できるなら出す、ということにした。

<span class="speaker">真砂</span>いい基準だ。

<span class="speaker">柊</span>あの夜に決めたことの中では、いちばん残ってる。緑だから出す、じゃなくて、緑の理由が言えるから出す。

<span class="speaker">真砂</span>一つめの夜と、同じところに戻ってきたね。

<span class="speaker">柊</span>戻ってきた。緑という色は、それ自体では何も言っていない。

</div>

<div class="dialogue">

<span class="speaker">真砂</span>最後に一つ。あの夜、いちばん効いた判断はどれだったと思う。

<span class="speaker">柊</span>手を止めたところ。零時すぎに、候補を出すのをやめて違いを書き出すことにした、あの十分。あそこで方向が変わってなかったら、朝まで時計を疑ってたと思う。

</div>

<div class="note">

後日、二人はこの一件を社内の振り返りで共有した。教訓として残ったのは修正手順ではなく、「行き詰まったら、まず自分の前提を疑え」という一行だった。ログは最初から答えを書いていたのだ。
</div>
