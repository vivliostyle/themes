# 鳴らなかったアラート {#night-1}

<p class="chapter-lead">2026年8月20日／通知ワーカー</p>

## 朝9時の問い合わせ

<div class="dialogue">

<span class="speaker">真砂</span>1つめの夜から始めようか。これ、正確には夜じゃなくて朝の話だよね。

<span class="speaker">柊</span>気づいたのが朝だっただけで、止まっていたのは前の晩から。8月19日の23時10分に通知ワーカーが何も処理しなくなって、それが分かったのが翌朝の9時20分。10時間あまり、誰も気づかなかった。

<span class="speaker">真砂</span>最初に気づいたのは問い合わせ窓口？

<span class="speaker">柊</span>そう。予約したのに確認の通知が来ない、という問い合わせが朝から3件続いて、窓口の人がおかしいと思って連絡をくれた。監視じゃなくて人間が見つけた。

<span class="speaker">真砂</span>そのとき、ダッシュボードは。

<span class="speaker">柊</span>全部、正常を示してた。開いた瞬間に、これは長引くなと思った。

</div>

<div class="note">

記録では、最初の連絡から原因の特定までに4時間近くかかっている。障害そのものは23時10分に始まっていたから、利用者から見た停止時間は14時間を超えた。復旧作業自体は10分で終わっている。

</div>

## 異常なしのダッシュボード

<div class="dialogue">

<span class="speaker">真砂</span>正常だった、というところをもう少し詳しく。何が正常を示していたの。

<span class="speaker">柊</span>ワーカーの健全性を示すパネルが3つあって、プロセスが生きているか、CPUとメモリが正常か、エラー率がしきい値以下か。この3つが全部、異常なしだった。

<span class="speaker">真砂</span>プロセスは実際に生きてたんだ。

<span class="speaker">柊</span>生きてた。落ちてはいない。CPUもメモリも正常範囲。というか、いつもより低いくらい。何も処理していないんだから当たり前なんだけど、そのときはそう読み取れなかった。

<span class="speaker">真砂</span>エラー率は。

<span class="speaker">柊</span>0％。これも異常なし。

<span class="speaker">真砂</span>そこがいちばん怖いところだよね。

<span class="speaker">柊</span>まったくその通り。エラー率が0だったのは、成功していたからじゃない。一件も処理していなかったから。分母がゼロだった。

</div>

<div class="note">

失敗の割合を測る指標は、処理そのものが行われなくなると意味を失う。分母がゼロでは割合を計算できないため、多くの監視システムはこの状態を「データなし」として扱う。問題は、その「データなし」を正常とみなすか異常とみなすかが、設定ひとつで決まってしまう点にある。

</div>

## 外から順に疑う

<div class="dialogue">

<span class="speaker">柊</span>最初に疑ったのは通知の配信業者。うちの外にあるから、疑うと気が楽なんだよね。

<span class="speaker">真砂</span>正直でよろしい。

<span class="speaker">柊</span>でも業者側の記録を見たら、そもそもうちから一件も送られていなかった。うちの中で止まってる。

<span class="speaker">真砂</span>次は。

<span class="speaker">柊</span>前日の夕方にリリースがあったから、その差分を全部洗った。通知テンプレートの文言を変える変更が入っていて、これが怪しいということになって30分かけて調べた。

<span class="speaker">真砂</span>でも違った。

<span class="speaker">柊</span>違った。文言を戻しても何も変わらない。そこでようやくキューを見た。

<span class="speaker">真砂</span>そこ、真っ先に見る場所じゃない？

<span class="speaker">柊</span>いま言われると本当にそう思う。未処理が4万件たまってた。23時10分から、ただの一件も減っていない。

</div>

> 犯人を外から順に疑うと、いちばん近い場所が最後に残る

## 分母がゼロだった

<div class="dialogue">

<span class="speaker">真砂</span>で、ワーカーは何をしていたの。生きてはいたわけだよね。

<span class="speaker">柊</span>接続待ちのループに入っていた。23時10分にキューとの接続が切れて、そのあとは再接続を試みては失敗する、をひと晩じゅう繰り返していた。

<span class="speaker">真砂</span>例外は投げないんだ。

<span class="speaker">柊</span>投げない。再接続は想定内の動作だから、警告のログが出るだけ。しかも警告は毎回同じ1行だから、量が多いだけで誰も読まない。

<span class="speaker">真砂</span>アラートの条件には入っていなかった。

<span class="speaker">柊</span>入っていなかった。うちのアラートは全部、何かが失敗したときに鳴るようにできていて、何も起きないときに鳴るものは一つもなかった。

<span class="speaker">真砂</span>止まっているのは失敗じゃない、という扱いになってたのか。

<span class="speaker">柊</span>そう。そしてとどめがこれ。処理件数のメトリクスは送られていたんだけど、値がゼロのときは送信しない実装になっていた。だから監視から見ると、その10時間はデータそのものが存在しない。

<span class="speaker">真砂</span>データなし。

<span class="speaker">柊</span>データなしのときにどう扱うか、という設定があって、既定値が「異常なしとみなす」だった。

</div>

<div class="note">

この既定値は、監視システムの導入時から誰も変えていない。当時の記録によれば、導入した担当者はメトリクスが一時的に欠けたときの誤検知を避けるため、あえて既定値のままにしたらしい。誤検知を減らすための設定が、そのまま見逃しを生む設定でもあった。

</div>

> 異常なしは、正常という意味ではなかった

## 沈黙を検知する

<div class="dialogue">

<span class="speaker">真砂</span>どうやって直したの。

<span class="speaker">柊</span>その場はワーカーを再起動して、10分で復旧した。たまっていた4万件も15分で処理しきった。問題はそこから先で、このままだと同じことがまた起きても、また10時間気づかない。

<span class="speaker">真砂</span>だから監視のほうを直した。

<span class="speaker">柊</span>3つ足した。1つめ、10分間の処理件数が0なら鳴らす。2つめ、データなしを異常として扱う。3つめ、0件のときもメトリクスを送る。

```yaml title="monitoring/rules.yml — 沈黙を異常として扱う"
- name: 通知ワーカーの処理が止まっている
  when: sum(jobs_done_10m) == 0
  for: 10m
  no_data: alert
  notify: [oncall]
```

<span class="speaker">真砂</span>`no_data: alert`の1行が今回の肝だよね。

<span class="speaker">柊</span>そう。この1行は他のルールにも全部入れた。30いくつあった既存のアラートのうち、データなしを異常として扱っていたのは2つだけだった。

<span class="speaker">真砂</span>残りは、黙ったまま壊れる余地があったと。

<span class="speaker">柊</span>あった。だからもう1つ、月に1度アラートを鳴らしてみる日を作った。検証環境でワーカーを止めて、10分待って、当番の端末が鳴るかどうかを確かめる。

<span class="speaker">真砂</span>鳴らないこともあるの。

<span class="speaker">柊</span>初回からいきなり2つ鳴らなかった。通知の宛先が、もう使っていないチャンネルのままだった。

</div>

<div class="dialogue">

<span class="speaker">真砂</span>10時間誰も気づかなかった、というのはチームの中でどう受け止められたの。

<span class="speaker">柊</span>最初は、当番だった人が責められる空気が少しあった。でも記録を見たら、その人は夜中に3回ダッシュボードを開いてる。

<span class="speaker">真砂</span>見てはいたんだ。

<span class="speaker">柊</span>見ていても気づけない画面だった。だから振り返りでは、誰が見落としたかの話をやめて、何が見えていれば気づけたかだけを書いた。

<span class="speaker">真砂</span>その答えは。

<span class="speaker">柊</span>キューの滞留件数。実はあの画面にも出てたんだよ。3番目のパネルの、下のほうに小さく。

<span class="speaker">真砂</span>出てはいたけど、目が行くのは異常なしの表示のほうだよね。

<span class="speaker">柊</span>そっちに目が行く。だから画面の並びも変えた。いちばん上に、いま処理が流れているかどうかだけを大きく出す。

<span class="speaker">真砂</span>件数じゃなくて。

<span class="speaker">柊</span>件数も出すけど、まず「流れている」か「止まっている」か。夜中の3時に読むなら、それくらい短いほうがいい。

</div>

<div class="note">

アラートは、設定しただけでは本当に鳴るかどうか分からない。鳴るべき状況をわざと作らないかぎり、その設定が正しいという証拠は最後まで得られないからだ。この会のあと、監視ルールには「これが壊れたとき何が鳴るか」を書く欄が追加された。
</div>
